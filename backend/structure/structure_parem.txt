────────────────────────────────────────────────────────────────────────────────
3.1. Trường tables — Bảng in sẵn trên đề (dạng THẬT hiện dùng: table_slot)
────────────────────────────────────────────────────────────────────────────────

sample_parem.json hiện dùng dạng FLAT "table_slot" — MỘT list phẳng liệt kê
TỪNG Ô của bảng (kể cả ô header/in sẵn), không phải cấu trúc lồng
columns[]/rows[].cells[] cũ. Đây là format duy nhất `_attach_table_slots()`
(pipeline.py, gọi trong load_barem) biết đọc.

{
  "table_id"  : "TB1",                  // ID bảng trong phần này (tùy ý, chỉ
                                        // để người đọc phân biệt nếu 1 part có
                                        // nhiều bảng).
  "table_slot": [                       // List phẳng, MỖI phần tử = 1 Ô trong
                                        // bảng — kể cả ô header/in sẵn, không
                                        // chỉ ô sinh viên điền.
    {
      "cell_id": "R1C1",                // ID ô = "{row_id}{col_id}" ghép liền,
                                        // không dấu phân cách.
      "source" : "printed",             // "printed"      = nội dung đề đã in
                                        //                  sẵn (header cột,
                                        //                  giá trị cố định như
                                        //                  "giả định sai") —
                                        //                  dùng field "text" ở
                                        //                  đây làm nội dung.
                                        // "student_text" = ô sinh viên tự điền —
                                        //                  "text" để rỗng ("");
                                        //                  nội dung thật được
                                        //                  tra theo cell_id từ
                                        //                  evidence.tables lúc
                                        //                  chấm (KHÔNG đọc từ
                                        //                  barem).
      "row_id" : "R1",
      "col_id" : "C1",
      "text"   : "Input"                // Chỉ có ý nghĩa khi source="printed".
    }
    // ... liệt kê đủ MỌI ô trong bảng, cả header lẫn ô sinh viên điền.
  ]
}

_attach_table_slots() gắn table_slot này vào MỌI criterion đã flatten có cùng
part_label với table đó — nên mọi criterion table trong cùng 1 part đều thấy
được khung bảng đầy đủ, không cần khai riêng lẻ.

table_slot chỉ dùng để CHẤM (grade_table_group_with_llm dùng nó dựng
table_text đầy đủ gồm cả header cho LLM xem) — KHÔNG bị validate_barem()
kiểm tra nội dung/tính nhất quán.

Ví dụ thật (câu 15 phần b — 3 ví dụ Input/Output, R1 là header, R4C2 là giá
trị in sẵn "giả định sai"):

  "tables": [
    {
      "table_id": "TB1",
      "table_slot": [
        {"cell_id":"R1C1","source":"printed","row_id":"R1","col_id":"C1","text":"Input"},
        {"cell_id":"R1C2","source":"printed","row_id":"R1","col_id":"C2","text":"Output"},
        {"cell_id":"R2C1","source":"student_text","row_id":"R2","col_id":"C1","text":""},
        {"cell_id":"R2C2","source":"student_text","row_id":"R2","col_id":"C2","text":""},
        {"cell_id":"R3C1","source":"student_text","row_id":"R3","col_id":"C1","text":""},
        {"cell_id":"R3C2","source":"student_text","row_id":"R3","col_id":"C2","text":""},
        {"cell_id":"R4C1","source":"student_text","row_id":"R4","col_id":"C1","text":""},
        {"cell_id":"R4C2","source":"printed","row_id":"R4","col_id":"C2","text":"'giả định sai'"}
      ]
    }
  ],
  "answer_slots": [
    {"slot_id":"cau_15_001_b_S1","cell_id":"R2C1","row_id":"R2","col_id":"C1"},
    {"slot_id":"cau_15_001_b_S2","cell_id":"R2C2","row_id":"R2","col_id":"C2"},
    {"slot_id":"cau_15_001_b_S3","cell_id":"R3C1","row_id":"R3","col_id":"C1"},

────────────────────────────────────────────────────────────────────────────────
4. grading_rule — TIÊU CHÍ ĐƠN (không có sub_criteria)
────────────────────────────────────────────────────────────────────────────────

Trường hợp đơn giản nhất: grading_rule là mảng gồm 1 hoặc nhiều tiêu chí LÁ,
mỗi tiêu chí chấm trực tiếp (không lồng sub_criteria bên trong). Mỗi tiêu chí
là 1 object — field set khác nhau tùy "question_type" (xem mục 7 để biết field
nào dùng cho mode nào), nhưng field CHUNG cho mọi criterion:

{
  "criterion_id"  : "T1"               // ID tiêu chí. Quy tắc đặt tên:
                                        //   T{số_câu}          — tiêu chí chính
                                        //   T{số_câu}{Phần}    — tiêu chí phần
                                        //                        (T13A, T13B)
                                        //   T{số_câu}_{part_label} — tiêu chí
                                        //                        theo slot đặc
                                        //                        biệt (T3_main_s1)
                                        // Ví dụ thật: T1, T3_main_s1, T3_main_s2,
                                        // T13A, T14C, T15B1.

  "question_type" : "matching"         // Loại câu hỏi của tiêu chí này —
                                        // BẮT BUỘC ở mọi criterion LÁ, quyết
                                        // định trực tiếp hàm chấm nào được gọi
                                        // (infer_criterion_grading_mode() đọc
                                        // ĐÚNG field này của CHÍNH criterion,
                                        // không có fallback lên cấp câu/cha
                                        // nữa). Đúng 4 giá trị hợp lệ — xem mục 7.

  "part_label"    : "main"             // Phần của câu hỏi tiêu chí này chấm.
                                        // Phải khớp với một part_label trong
                                        // question.parts[].

  "slot_ids"      : ["cau_1_001_main"] // Danh sách slot_id mà tiêu chí này
                                        // chấm điểm. BẮT BUỘC khai tay (không tự
                                        // tổng hợp từ answer_slots) —
                                        // get_student_evidence_for_slot() ưu
                                        // tiên lọc theo slot_ids (chính xác);
                                        // chỉ fallback lọc theo part_label (kém
                                        // chính xác hơn, có thể lẫn evidence của
                                        // slot khác cùng part) khi slot_ids
                                        // không khớp gì trong dữ liệu học sinh.

  "content"       : "Ghi đúng kết quả..."
                                        // QUY ƯỚC: content = TIÊU CHÍ CHẤM VÀ
                                        // CÁCH CHO ĐIỂM — mô tả criterion CẦN GÌ
                                        // VÀ quy tắc điểm bán phần bằng văn xuôi
                                        // (VD "Nếu đúng 2 hoặc 3 con số thì được
                                        // 0.25 điểm"). Đây là NGUỒN CHÍNH LLM
                                        // dùng để hiểu tiêu chí (đưa nguyên văn
                                        // vào prompt, mục === TIÊU CHÍ CHẤM ===).
                                        // Viết CÀNG CỤ THỂ càng tốt, đặc biệt nêu
                                        // rõ trường hợp biên/ví dụ sai nếu muốn
                                        // LLM áp dụng nhất quán (VD "'a=2' cũng
                                        // tính SAI") — nếu để mơ hồ, LLM có xu
                                        // hướng tự suy luận theo hướng dễ dãi hơn
                                        // (nguyên tắc "chấp nhận cách làm tương
                                        // đương" áp dụng mặc định cho hầu hết
                                        // criterion, xem mục 11).
                                        //
                                        // LƯU Ý DRIFT: với Matching, quy tắc bán
                                        // phần trong content (văn xuôi) và
                                        // partial_credit_rule (JSON, xem dưới)
                                        // MÔ TẢ CÙNG 1 LUẬT ở 2 dạng khác nhau —
                                        // 1 cho LLM đọc hiểu, 1 cho heuristic
                                        // Python thực thi. Sửa 1 bên PHẢI sửa
                                        // luôn bên kia, không thì LLM sẽ thấy 2
                                        // luật mâu thuẫn ngay trong cùng 1 prompt
                                        // (validate_barem() KHÔNG kiểm tra 2 field
                                        // này có khớp nhau không).

  "score"         : 0.5                // Điểm tối đa của tiêu chí (float).
                                        // 0 hợp lệ cho tiêu chí "phụ trợ" chỉ
                                        // dùng để xác minh dữ liệu (VD T8_main_s1
                                        // — sinh viên tự ghi STT để pipeline biết
                                        // input, không cộng điểm phần đó).

  "grader_note"   : "..."              // (Tùy chọn) QUY ƯỚC: grader_note = NHẮC
                                        // NHỞ CỦA GIÁO VIÊN — ngoại lệ, cách xử
                                        // lý case đặc biệt KHÔNG đã nêu trong
                                        // content, KHÔNG phải nơi lặp lại tiêu
                                        // chí/quy tắc điểm đã có trong content
                                        // (đó là việc của content, xem trên) —
                                        // nếu grader_note chỉ chép lại content
                                        // thì đang dùng sai field, nên xoá bớt.
                                        // Nếu criterion nằm trong sub_criteria
                                        // của 1 entry có sub_label, grader_note
                                        // của cha VÀ của chính nó (nếu có) được
                                        // MERGE (nối bằng "\n"), không cái nào
                                        // bị mất — xem mục 5.
}


──────── Field riêng theo "question_type": "matching" ────────

  "expected_outputs": ["3529"]         // Danh sách các dạng viết được chấp
                                        // nhận là đúng hoàn toàn (khớp CHÍNH
                                        // XÁC nguyên văn — _check_exact_output_match).
                                        // Chỉ 1 đáp án: ["3529"]. Nhiều dạng
                                        // chấp nhận: ["10/1/2026","10/01/2026"].
                                        //
                                        // GIÁ TRỊ ĐẶC BIỆT: nếu 1 phần tử của
                                        // list này TRÙNG TÊN 1 key trong sample
                                        // (VD "student_index"), pipeline tự
                                        // resolve thành GIÁ TRỊ THẬT của field đó
                                        // (prepare_output_evidence) — dùng để
                                        // khai "sinh viên phải ghi đúng STT của
                                        // mình" mà không cần hardcode số cụ thể
                                        // theo từng học sinh. Ví dụ thật:
                                        // "expected_outputs": ["student_index"]
                                        // (T3_main_s1, T8_main_s1).

  "expected_output_tokens": ["3","5","2","9"]
                                        // Output tách thành các token riêng lẻ,
                                        // dùng khi chấm bán phần theo VỊ TRÍ
                                        // (_grade_by_tokens, kết hợp
                                        // partial_credit_rule). KHÔNG bao giờ tự
                                        // nó tạo ra status="correct" dù khớp
                                        // 100% token — chỉ exact-match trên
                                        // expected_outputs mới cho "correct" (xem
                                        // mục 11). Để [] nếu không cần chấm bán
                                        // phần theo token.

  "partial_credit_rule": {             // (Tùy chọn) Quy tắc tính điểm bán phần
                                        // khi KHÔNG khớp expected_outputs tuyệt
                                        // đối nhưng có expected_output_tokens.
                                        //
                                        // CHỈ DÙNG CHO "matching" — field này chỉ
                                        // thực sự được heuristic tiêu thụ ở
                                        // _grade_by_tokens (Matching). Logical
                                        // (grade_expected_value_criterion)/Table
                                        // (grade_table_criterion) KHÔNG đọc field
                                        // này ở đâu cả. Nếu khai cho criterion
                                        // Logical/Table, nó vẫn bị leak vào prompt
                                        // (═ QUY TẮC ĐIỂM BÁN PHẦN ═, đọc chung
                                        // mọi question_type ở
                                        // _grade_with_llm_advised_core) nhưng chỉ
                                        // là text vô nghĩa — correct_token_count/
                                        // wrong_token_count là khái niệm token-
                                        // matching, Logical/Table không có
                                        // "token" nào để đếm. Muốn diễn đạt quy
                                        // tắc điểm bán phần cho Logical/Table,

7. LOẠI CÂU HỎI (question_type) — 4 GIÁ TRỊ HỢP LỆ DUY NHẤT
────────────────────────────────────────────────────────────────────────────────

KNOWN_QUESTION_TYPES (pipeline.py) chỉ đúng 4 giá trị. Mọi criterion LÁ (sau
flatten_criteria(), thực sự được chấm) PHẢI khai (hoặc kế thừa từ cha) 1 trong
4 giá trị này — infer_criterion_grading_mode() dùng string này để dispatch
TRỰC TIẾP sang hàm chấm tương ứng, không đoán qua field/evidence nào khác. Bất
kỳ giá trị nào khác 4 giá trị dưới đây (kể cả để trống) → rơi vào nhánh
"teacher_review" mặc định, KHÔNG có heuristic grader nào chạy.

  "matching"
      So khớp CHÍNH XÁC với đáp án đã biết trước (chuỗi/token theo vị trí).
      Pipeline: grade_expected_output_criterion() — dùng expected_outputs /
      expected_output_tokens / conditional_outputs / condition_source. Phù hợp
      cho đáp án có HÌNH THỨC cố định, đúng/sai rõ ràng theo từng ký tự (VD kết
      quả in ra màn hình của chương trình, STT tự ghi).

  "logical"
      Chấp nhận theo GIÁ TRỊ/LOGIC (không đòi khớp cấu trúc chặt như matching).
      Pipeline: grade_expected_value_criterion() — dùng expected_value
      {"keywords": [...], "sample_solution": "..."}, so khớp bằng
      value_matches_student_text() (word-boundary, linh hoạt hơn substring
      thường). Phù hợp cho đáp án là 1 đoạn logic/code mà cách trình bày có thể
      khác nhau (VD hàm C++ tự viết, công thức toán).

  "table"
      Sinh viên điền vào bảng (ví dụ/testcase). Pipeline: grade_table_criterion()
      /grade_table_row_criterion() — chấm ĐÚNG 1 Ô (row_id+col_id) mỗi
      criterion; run_part() gom mọi criterion table CÙNG PART thành 1 nhóm,
      chấm bằng 1 lần gọi LLM duy nhất (grade_table_group_with_llm) để LLM thấy
      được quan hệ giữa các ô cùng bảng.

  "visual"
      Sinh viên vẽ hình / lưu đồ. Pipeline: grade_visual_criterion() — Vision
      LLM đọc hình trực tiếp, KHÔNG qua bước LLM text (grade_with_llm_advised),
      không có heuristic advisory/blend.

  ── LƯU Ý PHÂN BIỆT matching vs logical ─────────────────────────────────
  Khác nhau ở ĐỘ CHẶT của việc so khớp, không phải ở loại dữ liệu. Matching =
  so khớp chuỗi/token chính xác (kèm điểm bán phần theo vị trí); logical =
  chấm theo từ khóa xuất hiện + để LLM tự đánh giá logic, KHÔNG có branch điểm
  thật ở heuristic (luôn score=0, needs_teacher_review).

  ── ROUTING THEO question_type CỦA TỪNG CRITERION (không theo cả câu) ──
  infer_criterion_grading_mode() đọc question_type của CHÍNH criterion đang
  chấm (criterion.get("question_type")), KHÔNG có fallback sang cấp câu/sample.
  Vì vậy câu 15 (nhiều ý a/b/c khác loại nhau: T15A=logical, T15B*=table,
  T15C=visual) route ĐÚNG theo từng ý, không bị "lây" loại của ý đầu tiên
  trong câu.

11. BẪY THƯỜNG GẶP KHI SOẠN BAREM
────────────────────────────────────────────────────────────────────────────────

  [!] KHÔNG đưa vào "keywords" (mode logical) một tên hàm/chữ ký mà ĐỀ ĐÃ IN
      SẴN cho sinh viên (sinh viên chỉ điền thân hàm, không viết lại chữ ký).
      Case thật đã xảy ra: T14C có keyword "InDSSV" trong khi đề đã in sẵn
      "void InDSSV(Sinhvien a[ ], int n)\n{ ...... \n}" — sinh viên chỉ viết
      phần "......" (thân hàm), KHÔNG BAO GIỜ gõ lại "InDSSV" — heuristic vì
      vậy LUÔN báo keyword này "missing", đẩy tín hiệu sai vào prompt LLM, khiến
      LLM hallucinate "bài làm thiếu khai báo hàm InDSSV" dù đề đã cho sẵn.
      Đã sửa: bỏ "InDSSV" khỏi keywords + thêm câu trong grader_note nói rõ chữ
      ký đã in sẵn, không được trừ điểm vì thiếu nó. Quy tắc chung: chỉ liệt kê
      keyword cho những gì sinh viên THỰC SỰ phải tự gõ ra.

  [!] Nếu đề có phần đã in sẵn/cho trước (chữ ký hàm, biến đã khai báo, giá trị
      cố định...), PHẢI ghi rõ trong "question.text"/"part.text" (để LLM đọc
      được qua khối "ĐỀ BÀI GỐC") — không đủ nếu chỉ có trong content, vì
      content mô tả TIÊU CHÍ chấm chứ không phải nguyên văn đề bài.

  [!] "content" mơ hồ → LLM tự suy luận theo hướng dễ dãi hơn (do có sẵn
      nguyên tắc "chấp nhận cách làm tương đương" áp dụng mặc định cho hầu hết
      criterion). Muốn chấm chặt ở điểm nào (VD "không được thêm ký tự thừa"),
      phải NÊU RÕ VÍ DỤ SAI cụ thể trong content, không thể trông chờ LLM tự
      đoán đúng ý giáo viên.

  [!] condition_source.type="self_reported" dùng key "slot_ids" (list) —
      KHÔNG phải "field". Nhầm sang "field" ở type này âm thầm resolve ra list
      rỗng rồi fallback đọc toàn bộ raw text của sinh viên (bug thật đã xảy ra ở
      T8_main_s2 lúc soạn barem, gây cảnh báo "no condition matched" tràn lan
      trên nhiều học sinh, chỉ phát hiện được qua soi field "value" trong log
      cảnh báo).

  [!] Mode "table": expected_value chỉ là VÍ DỤ GỢI Ý, không phải đáp án duy
      nhất được chấp nhận — đừng kỳ vọng nó dùng để so khớp cứng đúng/sai (đã
      bỏ hẳn cơ chế đó, xem CLAUDE.md "Table" và "Table batch grading").


────────────────────────────────────────────────────────────────────────────────
12. LƯU Ý KHI CHỈNH SỬA
────────────────────────────────────────────────────────────────────────────────

  [!] sample_parem.json là nguồn gốc (source of truth). Chỉnh sửa file này khi
      muốn thay đổi rubric.

  [!] JSON không hỗ trợ comment (//). Không được viết comment trong file JSON —
      các đoạn "//..." trong tài liệu này chỉ để giải thích, không sao chép
      nguyên văn vào sample_parem.json.

  [!] Điểm của tất cả criterion LÁ (sau flatten, tính theo group_max_score cho
      các group all_or_nothing — chỉ cộng 1 lần/nhóm) phải cộng lại bằng
      total_score khai ở đầu file — validate_barem() báo lỗi nếu lệch.

  [!] Mỗi criterion LÁ (kể cả sub_criteria con) PHẢI có "question_type" — tự
      khai hoặc kế thừa từ cha (part_label/question_type/slot_ids kế thừa;
      grader_note MERGE, xem mục 5). Chỉ 4 giá trị hợp lệ, xem mục 7.

  [!] load_barem() tự động chạy validate_barem() mỗi khi đọc sample_parem.json
      và in cảnh báo/lỗi ra console. Các lỗi bị bắt (chặn chạy):
        - criterion_id trùng lặp
        - score = null nhưng KHÔNG thuộc group all_or_nothing (không nơi nào
          bù điểm cho tiêu chí này)
        - score âm
        - group all_or_nothing có group_max_score không nhất quán giữa các
          thành viên
        - tổng điểm toàn barem khác total_score khai báo ở đầu file
      Cảnh báo (không chặn chạy): thiếu question_type, question_type lạ (không
      nằm trong 4 giá trị mục 7, kể cả ở wrapper — vô hại nếu wrapper không bao
      giờ được chấm trực tiếp), group chỉ có 1 thành viên. validate_barem()
      KHÔNG kiểm tra NỘI DUNG các field như condition_source/table_slot (chỉ
      kiểm cấu trúc điểm số) — 1 condition_source sai key (VD "field" thay vì
      "slot_ids" ở self_reported) sẽ load im lặng, chỉ lộ ra lúc chấm thật qua
      log cảnh báo runtime, không phải lúc load_barem().

  [!] Sửa xong sample_parem.json nên chạy `python pipeline.py --test` hoặc gọi
      thử load_barem() để xem console có báo lỗi/cảnh báo không, trước khi
      chấm thật (tốn phí LLM).
